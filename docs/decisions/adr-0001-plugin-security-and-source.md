# ADR-0001：插件安全边界与插件来源

> 决策状态：**accepted**（2026-08-15）
> 关联待定项：`docs/architecture/01-overview.md` §7、`docs/architecture/02-plugin-model.md` §10

## 背景（Context）

Keystone采用"配置驱动、多实例隔离、热重载、中间件管道"的插件执行模型，插件以单文件 `.cs` + manifest 的形式由宿主加载（Roslyn 内存编译 + 私有 ALC，见 `docs/architecture/02-plugin-model.md` §4-§7）。

方案总览与插件模型文档各列出了一项未决问题（`docs/architecture/01-overview.md` §7 待定决策；`docs/architecture/02-plugin-model.md` §10 待定）：

1. **安全边界**：插件按可信代码同进程执行，还是独立进程隔离？
2. **插件来源**：插件仅从本地文件加载，还是支持远程分发（版本/签名管理）？

两项决策相互耦合：来源决定威胁模型，威胁模型反过来约束来源范围。本 ADR 汇总两个前置分析子任务的结论（插件安全边界分析、插件来源模型分析），固化默认决策与演进路径，消除架构文档中的待定项。

## 决策（Decision）

### 决策 1：插件安全模型 — 同进程可信代码（默认）

**采用方案 A：插件作为同进程可信代码执行**，作为当前唯一支持的运行形态。

- 信任边界 = 用户：能放置插件文件到约定位置的人，即对宿主拥有同等信任等级。
- 为方案 B（独立进程隔离）**预留 `IPluginHost` 扩展点**，作为未来可选形态，不进入本期默认配置。
- 安全防护不在进程边界实现，而是通过**来源可信度分级**（见决策 2 演进路径）+ 宿主侧缓解措施实现（见权衡/风险）。

### 决策 2：插件来源 — 本地文件（初始），经 `IPluginSource` 抽象支持远程演进

**采用方案 A：插件来源初始为本地文件**——插件由用户手动放置到约定目录，manifest 记录版本（manifest 已含 `version` 字段，见 `docs/architecture/02-plugin-model.md` §1）。

演进路径（获取端演进，加载管线不动）：

1. **本地文件 + 版本记录**（初始落地）：manifest 记录版本，宿主按插件 ID 识别。
2. **本地文件 + 签名校验**（后续增强）：宿主内置公钥，对插件文件做签名验证，来源可信度从"手动放置"升级为"密码学验证"。
3. **远程分发**（远期可选）：通过 `IPluginSource` 抽象引入远程获取端，**只替换获取端，不改变编译/ALC/dispose 加载管线**（获取与加载解耦）。

## 理由（Rationale）

### 安全模型选 A（同进程可信代码）

1. **威胁模型与来源一致**：决策 2 初始来源 = 本地文件，能写文件的用户已拥有宿主同等权限，进程隔离的防御收益为空转。
2. **.NET 5+ 无官方进程内沙箱**：CAS 已移除、AppDomain 沙箱不可用，进程内隔离没有开箱方案，自己实现成本高且不可信。
3. **零成本兼容既有决策**：方案 A 与 ALC/热重载/调试/disposer 协议（D5、`02-plugin-model.md` §4-§7）天然兼容，不新增机制。
4. **性能原则不破坏**：域内插件直接调用是 `01-overview.md` §6 的克制边界；进程隔离会强制跨进程调用，推翻该原则。

### 来源选 A（本地文件）

1. **版本/签名不是远程分发的专属能力**：本地文件同样可逐步引入版本记录与签名校验（演进路径 1→2），远程分发不解决本地无法解决的问题。
2. **与 Roslyn 内存编译决策冲突**：远程分发 DLL 会推翻"单文件 .cs 内存编译"（D5）；远程分发源码则引入缓存膨胀与更新协调复杂度。
3. **与安全模型联动**：远程不受控来源会打破同进程可信威胁模型，迫使进程隔离（成本约 5-10 倍，见下）——本期来源决策为安全模型守住边界。
4. **设计期资源有限**：远程分发是纯基础设施投入，不验证核心插件模型，放到获取端抽象之后按需引入。

## 权衡 / 风险（Trade-offs / Risks）

### 方案 A（同进程可信代码）的已接受成本

| 风险 | 说明 | 缓解 |
|------|------|------|
| CPU 死循环无法进程内中断 | 插件死循环会卡死整个宿主进程 | 超时 + 熔断 + 监督（`05-reliability.md` 已有监督策略） |
| 恶意/缺陷插件可触及宿主全部能力 | P/Invoke、反射、直接调用宿主 API 均可能 | 接口白名单 + 宿主侧执行器 + Roslyn analyzer 静态检查 |
| 无硬性进程级资源限制 | 内存/文件句柄等资源不受限 | 插件级资源指标 + 外部监督者（后续增强） |

### 方案 B（独立进程隔离）的代价

- **成本约为方案 A 的 5-10 倍**：进程编排、IPC 契约、生命周期同步、调试复杂度。
- **推翻性能原则**：域内直接调用变为跨进程调用，`01-overview.md` §6 明确不做全 actor 化，隔离进程与该原则冲突。
- 故 B 仅作为 `IPluginHost` 扩展点预留，不进入本期。

### 来源方案的权衡

- **无来源验证**：初始阶段插件文件无签名校验，信任完全落在用户放置动作上。
- **更新靠手动**：无远程渠道，插件升级由用户替换文件完成（FileSystemWatcher 热重载触发，机制已存在）。
- 上述两点由演进路径 2（签名校验）与 3（远程分发）在后续阶段补足，不阻塞本期设计。

## 备选方案（Alternatives）

### 安全模型

- **方案 B（独立进程隔离）**：见权衡表，成本 5-10 倍且推翻域内直接调用原则，本期否决，作为 `IPluginHost` 扩展点保留。
- **方案 C（进程内沙箱/受限执行）**：.NET 5+ 无官方支撑（CAS/AppDomain 沙箱已移除），自制不可信，否决。

### 插件来源

- **方案 B（远程分发为默认）**：与 Roslyn 内存编译（D5）冲突、破坏同进程可信威胁模型、纯基础设施投入，本期否决。
- **方案 C（本地 + 远程双轨并行）**：同时维护两套获取端，增加设计期复杂度，无实际用户需求支撑，否决。

## 影响（Impact）

- **架构文档**：`docs/architecture/01-overview.md` §7 与 `docs/architecture/02-plugin-model.md` §10 的"安全边界""插件来源"待定项由本 ADR 收敛为已决。
- **加载管线**：编译（Roslyn 内存编译）、加载（私有 ALC）、回收（disposer 协议）、热重载流程全部按同进程可信代码设计，无进程边界代码。
- **接口面**：加载侧引入 `IPluginSource`（获取端抽象）与 `IPluginHost`（运行形态扩展点）两个抽象边界；本期仅实现本地文件获取端与同进程宿主，远程分发/进程隔离走抽象扩展。
- **安全职责**：本期安全职责 = 来源可信度分级（用户放置→签名校验）+ 宿主侧缓解（接口白名单/超时熔断/静态检查），不做进程级隔离。
- **不回退项**：后续引入远程分发不得破坏"获取与加载解耦"约束；引入进程隔离不得推翻"域内直接调用"性能原则。
